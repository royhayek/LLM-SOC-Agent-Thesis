# F2 — MQTT credential guessing (`mqtt_brute_force`)

Ticket E1-09 (SCRUM-96). Method: ADR-0003. Predicted visibility (`attack_families.yaml`):
mqtt yes, flows yes, honeypot no.

## What it does

A compromised IoT device D guesses broker credentials: one CONNECT per guess from the fixed
list `scenarios/mqtt_credentials.txt` (25 common weak logins, none matching a real testbed
login), each with a wrong password, so the broker refuses and logs it. The attack runs in D's
own emulator container with client id `<D>-brute`, at a fixed 0.3 s attempt rate. Needs broker
authentication, which is on (ADR-0003, E1-05). Bounded by the list, so it exits 0.

## Sources that received traces

Measured over two same-seed runs on `iot-temp-01`, 40 s episodes (`test_f2_run.py`, 2026-10-06):

| Source | Trace | Count per run |
|---|---|---|
| mqtt | yes | 25 refused-auth lines in `broker.log` for `iot-temp-01-brute` (one per guess) |
| flows | yes | 27 flows for the device (25 refused CONNECTs plus two benign connections) |
| honeypot | no | 0 events |

Observed visibility matches the predicted matrix. The refused logins are the MQTT source's
record of the attack; `mqtt.log` (the subscriber) shows nothing, because a refused CONNECT
publishes nothing. This is why E1-05 keeps `broker.log` as part of the MQTT telemetry.

## Repeatability

Raw counts over two same-seed runs are compared within the F2 tolerance in
`tests/attack_tolerance.yaml` (mqtt 0.10, flows 0.20). Both runs gave 25 refused attempts and
27 device flows. Benign wrong-password irregularities (E1-05, 2 per hour) are rare enough that
in a 40 s episode they do not disturb the count; the brute client id separates the attack's
refusals from any benign one.
