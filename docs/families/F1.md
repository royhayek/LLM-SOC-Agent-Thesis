# F1 — MQTT publish flood (`mqtt_publish_flood`)

Ticket E1-08 (SCRUM-87). Method: ADR-0003. Predicted visibility (`attack_families.yaml`):
mqtt yes, flows yes, honeypot no.

## What it does

A compromised IoT device D floods the broker with PUBLISH messages over one connection, using
`mosquitto_pub` in D's own emulator container and D's own credentials. Fixed parameters: 3000
messages, 0.02 s apart (~60 s), 256-byte payload, QoS 0, topic `iot/<D>/flood`. Bounded by the
message count, so it finishes inside the episode and exits 0.

## Sources that received traces

Measured over four runs on `iot-temp-01`, 75 s episodes (`test_f1_run.py`, 2026-10-06):

| Source | Trace | Count per run |
|---|---|---|
| mqtt | yes | 2719–3000 flood messages in `mqtt.log` |
| flows | yes | 3 flows for the device (flood + two benign connections) |
| honeypot | no | 0 events |

Observed visibility matches the predicted matrix.

## Repeatability

Raw counts over two same-seed runs are compared within the F1 tolerance in
`tests/attack_tolerance.yaml` (mqtt 0.15, flows 0.20). The flood sends a fixed 3000 messages,
but at QoS 0 the burst overruns the subscriber, so the logged count varies (2719–3000, ~9 %
over the first two runs); the tolerance covers this. The device's flow count was 3 in every run.
