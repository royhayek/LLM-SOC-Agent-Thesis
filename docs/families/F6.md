# F6 — TCP SYN flood (`syn_flood`)

Ticket E1-13 (SCRUM-117). Method: ADR-0003. Predicted visibility (`attack_families.yaml`):
mqtt no, flows yes, honeypot no. The one-source family: it lets H1 separate "gain from fusion"
from "gain from having a source at all" (risk #4).

## What it does

An external attacker host floods an IoT device D directly with TCP SYN packets, using hping3
(`--syn --flood`), on a fixed non-MQTT destination port (80), for a fixed 5 s. The flood runs in
the `attacker` container and addresses D by IP, not through the broker. Bounded by `timeout`, so
it exits 0.

## Source port is fixed (parameter choice)

ADR-0003 fixes the destination port and duration and leaves the source port open. hping3's
default increments the source port, so NFStream records one flow per SYN: a 5 s flood produced
~61,000 flows and a 144 MB flow file. The flood is run with a fixed source port (`-k -s 53535`),
so it is one flow carrying all the SYN packets instead: ~238,000 SYN packets in a 29 KB flow
file. This keeps the flood a single flow and keeps the dataset manageable, while remaining a
`--syn --flood`. ADR-0003's F6 risk ("a flood can saturate the capture sidecar and drop flow
records") is the reason.

## Sources that received traces

Measured over four runs on `iot-cam-01`, 20 s episodes with a 5 s flood (`test_f6_run.py`,
2026-10-06):

| Source | Trace | Count per run |
|---|---|---|
| mqtt | no | 0 attack messages (benign publishes continue) |
| flows | yes | 1 flow to the device on port 80, carrying ~236,000–239,000 SYN packets |
| honeypot | no | 0 events |

Observed visibility matches the predicted matrix.

## Repeatability

Raw counts over two same-seed runs are compared within the F6 tolerance in
`tests/attack_tolerance.yaml` (flows 0.50, packets 0.20). The flow count is always 1; the SYN
packet count is the flood's volume and was 239,325 vs 236,595 over two runs (~1 %), well inside
the tolerance, which is wider to absorb host-load variation.
